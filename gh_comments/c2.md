Independent data point for the VRAM figure driving this: for `unsloth/Qwen3.8-Flash-Next-GGUF` the ~4-bit tier (UD-Q4_K_XL, unsloth's Q4_K_M-class upload) is a 111.3 GB file measured from the HF API (split shards summed); with KV cache + runtime overhead at 8K context the realistic requirement is ~135 GB. We track every quant of this model daily: https://modelfit-eight.vercel.app/unsloth-qwen3-8-flash-next-gguf/

The relevant point for the stock-filtering decision: this is genuinely a >100 GB model, so the H200 141GB / Blackwell tier is the *only* viable single-GPU target — an A100 80GB fallback can't satisfy it no matter what. That makes dropping the low-stock H200 actively harmful here (your point #1): for the top VRAM tier there often is no higher-stock equivalent to fall back to, so filtering it out turns a satisfiable request into "criteria-unsatisfiable." A `--allow-low-stock` opt-in plus a graceful next-best-attempt on provisioning failure seems like the right risk tradeoff, since the high-VRAM tier is exactly where low-stock and no-alternative coincide.
